# Database Schema

This document describes the Firestore and Cloud Storage schema used by the news app for
journalist-authored articles. The schema is enforced by [`firestore.rules`](../firestore.rules)
and [`storage.rules`](../storage.rules); every constraint listed here has a matching rule.

## Design goals

1. **Mirror the domain entity.** The app already models an article as
   `author, title, description, url, urlToImage, publishedAt, content` (see
   `frontend/lib/features/daily_news/domain/entities/article.dart`). User-authored articles keep
   the same vocabulary so the presentation layer renders both remote (NewsAPI) and own articles
   through the same `ArticleEntity`.
2. **Flat and query-friendly.** Articles live in a single top-level collection ordered by
   `publishedAt`. That is the only query the feed needs, and a single-field index is created
   automatically by Firestore.
3. **Storage and Firestore stay consistent.** Thumbnails are files in Cloud Storage; Firestore
   stores a reference to them. The reference is validated by rules so a document can never point
   outside the `media/articles/` folder.
4. **Server-owned timestamps.** `createdAt` and `updatedAt` must be written with the server
   timestamp so clients cannot forge them.

## Firestore

```
(root)
└── articles                          # collection
    └── {articleId}                   # document, auto-generated id
        ├── title          : string
        ├── description    : string | null
        ├── content        : string
        ├── author         : string
        ├── authorId       : string   # Firebase Auth uid of the journalist
        ├── category       : string   # one of the seven feed categories
        ├── thumbnailURL   : string | null   # download URL of the Storage object
        ├── thumbnailPath  : string | null   # Storage object path: media/articles/{fileName}
        ├── publishedAt    : timestamp
        ├── createdAt      : timestamp
        └── updatedAt      : timestamp
```

### `articles/{articleId}`

| Field           | Type        | Required | Constraint                                                                                   | Purpose                                                        |
|-----------------|-------------|----------|----------------------------------------------------------------------------------------------|----------------------------------------------------------------|
| `title`         | `string`    | yes      | 1–150 chars                                                                                  | Headline shown in the feed and detail screen                   |
| `description`   | `string`    | no       | `null` or 1–300 chars                                                                        | Short summary shown in the feed tile; absent rows show no teaser |
| `content`       | `string`    | yes      | 1–20 000 chars                                                                               | Full article body                                              |
| `author`        | `string`    | yes      | 1–80 chars                                                                                   | Display name of the journalist                                 |
| `authorId`      | `string`    | yes      | Equals `request.auth.uid` on create; immutable afterwards                                    | Ownership: only the author may update or delete                |
| `category`      | `string`    | yes      | One of `general, business, technology, science, health, sports, entertainment`               | Feed filter, search chips and the Brief                        |
| `thumbnailURL`  | `string`    | no       | `null`, or a Firebase Storage download URL whose object path starts with `media/articles/`   | Ready-to-render image URL for cached images                    |
| `thumbnailPath` | `string`    | no       | `null`, or matches `^media/articles/[^/]+$`; must be `null` exactly when `thumbnailURL` is   | Storage path, used to delete or replace the file               |
| `publishedAt`   | `timestamp` | yes      | Any timestamp                                                                                | Ordering key for the feed; journalist may schedule/backdate    |
| `createdAt`     | `timestamp` | yes      | Must equal `request.time` on create; immutable afterwards                                    | Audit                                                          |
| `updatedAt`     | `timestamp` | yes      | Must equal `request.time` on create and on every update                                      | Audit / cache invalidation                                     |

No other fields are accepted (`keys().hasOnly`). The document id is generated by the client SDK
(`collection('articles').doc()`) and is exposed to the app as `ArticleEntity.id`.

### Why both `thumbnailURL` and `thumbnailPath`?

The assignment requires a reference to the Storage object. A download URL alone is enough to
render the image but is awkward to validate and impossible to delete from (the object path is
URL-encoded inside it). The plain path is trivial to validate and to pass to
`FirebaseStorage.ref(path).delete()`, but needs a network round-trip to become a renderable URL.
Storing both keeps reads cheap and writes safe. The rules check that the two agree on the folder.

### Example document

```json
{
  "title": "City council approves new bike lanes",
  "description": "Twelve kilometres of protected lanes will be built downtown by 2027.",
  "content": "The city council voted 9–2 on Tuesday to approve ...",
  "author": "Nelson Rojas",
  "thumbnailURL": "https://firebasestorage.googleapis.com/v0/b/back-pruebasymmetry.firebasestorage.app/o/media%2Farticles%2F8f1c2e6a-bike-lanes.jpg?alt=media&token=3d2c…",
  "thumbnailPath": "media/articles/8f1c2e6a-bike-lanes.jpg",
  "publishedAt": "2026-09-15T10:00:00Z",
  "createdAt": "2026-09-15T09:58:12Z",
  "updatedAt": "2026-09-15T09:58:12Z"
}
```

## Cloud Storage

```
bucket: back-pruebasymmetry.firebasestorage.app
└── media/
    └── articles/
        └── {fileName}     # e.g. 8f1c2e6a-bike-lanes.jpg
```

| Rule                    | Value                                   |
|-------------------------|-----------------------------------------|
| Allowed folder          | `media/articles/` only, no sub-folders  |
| Allowed content types   | `image/jpeg`, `image/png`, `image/webp` |
| Maximum size            | 5 MiB                                   |
| Read                    | public                                  |
| Create / replace        | allowed if type and size are valid      |
| Delete                  | allowed                                 |

File names are generated by the app as `{uuid}-{slug}.{ext}` so two journalists uploading
`photo.jpg` never collide.

## Access model

Firebase Authentication (email/password and Google) is enabled. The rules combine schema
enforcement with ownership:

| Operation | Firestore `articles/{id}`                                   | Storage `media/articles/{file}`          |
|-----------|-------------------------------------------------------------|------------------------------------------|
| read      | anyone                                                      | anyone                                   |
| create    | signed in and `authorId == request.auth.uid`                | signed in, valid type and size           |
| update    | signed in and `resource.data.authorId == request.auth.uid`; `authorId` and `createdAt` immutable | signed in, valid type and size |
| delete    | signed in and `resource.data.authorId == request.auth.uid`  | signed in                                |

The feed stays public so readers never need an account; writing needs one so an article can
always be traced to its author and nobody can edit somebody else's work.

## Cloud Functions

`functions/index.js` exposes one callable function, `assistArticle` (region `us-central1`,
Node 22). It is the only place that talks to the language model (Claude, model
`claude-haiku-4-5-20251001`); the API key lives in the Firebase secret `ANTHROPIC_API_KEY` and
never reaches the app.

| Request field | Type   | Rule                                                                 |
|---------------|--------|----------------------------------------------------------------------|
| `task`        | string | `suggest`, `brief`, `plain` or `translate`                           |
| `title`       | string | optional, up to 150 characters                                       |
| `content`     | string | required, 1 to 20 000 characters (same cap as `articles.content`)     |
| `language`    | string | `translate` only: `es` (default), `en`, `pt`, `fr`                   |

| Task        | Answer                                                              |
|-------------|---------------------------------------------------------------------|
| `suggest`   | `{ headlines: [up to 3], summary: string, category: string }`       |
| `brief`     | `{ bullets: [up to 3] }`                                            |
| `plain`     | `{ text: string }`                                                  |
| `translate` | `{ text: string }`                                                  |

Callers must be signed in (`unauthenticated` otherwise). Bad input answers `invalid-argument`,
model rate limits `resource-exhausted`, outages `unavailable`, and an unusable model answer
`internal`. Run `npm test` inside `functions/` for the unit tests (validation, prompts and the
handler with a fake model client; no network).

## Upload flow

1. Client generates `articleId = db.collection('articles').doc().id`.
2. Client uploads the image to `media/articles/{uuid}-{slug}.{ext}`; Storage rules validate type
   and size.
3. Client obtains the download URL and writes the Firestore document with `thumbnailURL`,
   `thumbnailPath` (both `null` when there is no photo), `authorId`, `category` and
   `FieldValue.serverTimestamp()` for `createdAt` / `updatedAt`.
4. If step 3 fails the client deletes the uploaded file so no orphan objects are left.

## Future extensions (not in scope)

- `articles/{id}/comments/{commentId}` sub-collection for reader comments.
- A composite index `(category asc, publishedAt desc)` if the feed ever filters own articles by
  category server-side (today the category is only used client-side).
- `authors/{uid}` profile collection (bio, avatar) once profiles become editable.
